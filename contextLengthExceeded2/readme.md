# contextLengthExceeded2 — 策略二：摘要压缩

多轮对话上下文管理示例。把「最近若干条对话」保留原文，更早的内容调用一次模型压成摘要，从而让**发送给模型的上下文长度不再随轮次增长**，同时不丢失早期关键信息。

与策略一（`../contextLengthExceeded/`，滑动窗口）互补：策略一「只丢不记」，本示例「有损但有记忆」。

## 要解决的问题

不管理历史会同时撞上三件事：

| 压力 | 表现 |
| --- | --- |
| 窗口上限 | 模型有上下文窗口上限（如 128K token），超出直接报错 |
| 成本 | 上下文每一轮都要重发，token 按量计费，历史越长越贵 |
| 注意力稀释 | 上下文越长，早期关键信息的权重越低（lost in the middle） |

## 核心思路

> **近期的原文保真、远期的历史压成摘要。**
>
> 发送给模型的上下文由三段构成：固定人设 + 一条滚动摘要 + 最近若干条原文。长度不再与轮次挂钩。

```text
发给模型的 context（长度有界）            本地 history（全量保留，不发送）
┌────────────────────────────────┐
│ system    人设（固定不动）       │       ┌──────────────────┐
│ system    【此前对话摘要】（滚动） │  ◀──  │ 全部原文          │
│ user      最近第 N-2 轮提问      │       │ 含已被压缩的早期轮次│
│ assistant …                    │       │ 方便换策略、做回溯  │
│ user      最近第 N 轮提问        │       └──────────────────┘
└────────────────────────────────┘
```

三层各有分工，压缩力度按「时间距离」分层：

| 层 | 内容 | 策略 | 理由 |
| --- | --- | --- | --- |
| 人设 | 第一条 system | 永远保留 | 它是行为约束，丢了整个会话的性格就变了 |
| 摘要 | 带 `【此前对话摘要】` 前缀的 system | 滚动重写，长度有上限 | 只留结论，替掉大段原文 |
| 近期 | 最近 `keep_recent` 条 | 原文保留 | 当前话题的细节最重要，摘要会磨掉 |

## 一轮对话里发生了什么

```text
1. chat(user_input)
   └─ history.append({"role": "user", ...})

2. summarize_old_messages(history)
   ├─ 按 role 拆成三段：人设 / 旧摘要 / 对话
   ├─ 判断 len(dialog) <= keep_recent
   │    └─ 是 → 原样返回 history（不用压缩，也不调用模型）
   └─ 否 → 切出 old（过期）与 recent（保留）
        ├─ 把「上一条摘要」+「old 原文」拼起来重新摘要（滚动）
        └─ 返回 [人设] + [新摘要] + [recent]

3. runDemo(messages=上一步的结果)
   └─ 只发送压缩后的窗口

4. history.append({"role": "assistant", ...})
   └─ 本地 history 仍记全量，不裁剪
```

## 与策略一对比

同一份 40 轮对话，三种做法的上下文长度实测（摘要固定按 200 字模拟）：

| 轮次 | 不管理（条数/字数） | 策略一（条数/字数） | 策略二（条数/字数） |
| --- | --- | --- | --- |
| 1 | 3 / 64 | 2 / 36 | 3 / 64 |
| 5 | 11 / 244 | 7 / 154 | 7 / 293 |
| 10 | 21 / 472 | 7 / 156 | 7 / 295 |
| 20 | 41 / 952 | 7 / 163 | 7 / 301 |
| 30 | 61 / 1432 | 7 / 163 | 7 / 301 |
| 40 | 81 / 1912 | 7 / 163 | 7 / 301 |

两条关键结论：

- **长度都稳定了**：不管理是线性增长（40 轮 1912 字），后两者都稳定在 7 条消息，不再随轮次变化。
- **策略二比策略一多花约一倍字数**（301 对 163），买回来的正是「早期说过的人名、数字、结论还在摘要里」。

| 维度 | 策略一：滑动窗口 | 策略二：摘要压缩 |
| --- | --- | --- |
| 长度控制 | 稳定 | 稳定 |
| 早期信息 | **直接丢弃** | 保留要点（有损） |
| 额外 API 调用 | 无 | 超过阈值后每轮 1 次 |
| 实现复杂度 | 低 | 中（要写摘要 prompt、防摘要失真） |
| 适用 | 短会话、演示、调试 | 长会话、客服、陪伴、连续编码 |

## 实现中的五个关键决策

**① 三层分工，而不是一刀切**
人设永远保留、近期原文保留、中间部分才压。见上表。

**② 阈值判断用「小于等于」而非「小于」**

```python
if len(dialog) <= keep_recent:
    return history
```

正好卡在阈值上时不压缩，真正超了才动手。若写成 `<`，聊到边界那两条会连续触发两次压缩，多花两次调用。**比的是「对话条数」而不是 `len(history)`**，这样人设和摘要占掉的名额不会算歪。

**③ 滚动摘要：必须带上一条摘要一起重压**

```python
pieces = [m["content"] for m in old_summaries]      # 上一条摘要
pieces += [f"{m['role']}: {m['content']}" for m in old]   # 这次过期的原文
new_summary = summarize("\n".join(pieces))
```

只压 `old` 而丢掉上一条摘要，**从第二次压缩开始最早的对话就永久消失了**（摘要只有一层，不叠加）。合并重压之后摘要永远只有 1 条，不会越滚越多。

**④ 窗口切在 user 边界上**

```python
start = max(0, len(dialog) - keep_recent)
while start < len(dialog) and dialog[start]["role"] != "user":
    start += 1
```

一轮对话是「问 + 答」两件事，从中间切开会留下孤立的 assistant 消息，部分模型遇到「首条是 assistant」直接返回 400。所以往后挪到最近的 user——**宁可少带一条，不能带半轮**。

**⑤ 发送与存储分离**
本地 `history` 保留全量原文，只是不发送。好处是随时能换策略、能回溯真实对话；代价是内存不回收，超长会话要考虑落盘或裁剪。

**按 role 拆段，而不是按下标取值。** 摘要消息本身也是 system 角色，一旦它出现，`history[0]` / `history[1:]` 这类下标假设就全歪了：

```python
persona = [m for m in history
           if m["role"] == "system" and not m["content"].startswith(SUMMARY_PREFIX)]
dialog  = [m for m in history if m["role"] != "system"]
```

用字段判断代替位置假设，压缩跑过多少次都不会错。

## 要付的代价

| 代价 | 说明 | 缓解 |
| --- | --- | --- |
| 有损 | 摘要不可逆，细节（精确报错、原始数字）大概率丢失 | 保住「最近 `keep_recent` 条原文」这个保真区 |
| 每轮多一次调用 | 超过阈值后每轮都重压一次摘要 | 改成「攒够一批再压」的增量式 |
| 失真累积 | 摘要是「摘要的摘要」滚出来的，压太多次会偏离事实 | prompt 里只保留可验证事实（人名、数字、已确认结论） |
| 单会话限制 | `history` 是模块级全局变量，多用户会串话 | 做服务时把状态挪进 session 对象或字典 |

## 三种策略的适用边界

| 场景 | 该用哪种 | 理由 |
| --- | --- | --- |
| 短会话、调试、演示 | 滑动窗口（策略一） | 实现最简，长度可控，不额外花钱 |
| 长会话（客服、陪伴、连续编码） | 摘要压缩（策略二） | 需要跨轮次记忆，又不能无限增长 |
| 知识量远超对话（文档问答、知识库） | RAG 检索 | 信息不在对话里，压也没用，要按需检索 |

三者并不互斥：生产系统常见的是「摘要 + 最近原文窗口 + 检索」叠着用。本示例的骨架已可扩展，把 `summarize_old_messages()` 换成「摘要 + 检索」的组合函数即可。

## 如何运行

**在本目录内执行**（`run.py` 与本文件同目录）：

```bash
python index.py
```

示例会连续提四个问题，最后打印「最后一次真正发给模型的消息结构」，可以直接看到摘要与窗口的样子：

```text
=== 最后一次发给模型的消息（共 7 条）===
[   system] 你是一个简洁的助手，回答不超过两句话。
[   system] 【此前对话摘要】JSON 是一种轻量级文本数据交换格式…
[     user] 什么是 HTTP 状态码？
[assistant] HTTP 状态码是服务器在响应中返回的三位数字代码…
[     user] 什么是 REST？
[assistant] REST 是一种基于 HTTP 的软件架构风格…
[     user] 什么是 WebSocket？
```

> 本目录名含连字符（`contextLengthExceeded2`），不是合法的 Python 包名，无法从项目根写 `from contextLengthExceeded2.run import runDemo`。同目录内 `from run import runDemo` 不受影响。

**在别的文件里调用**

```python
from index import chat, summarize_old_messages

answer = chat("什么是 JSON？")                        # 追加一轮，返回回答正文
ctx = summarize_old_messages(history, keep_recent=4)  # 只看压缩后的窗口，不发请求
```

**参数**

| 函数 | 参数 | 默认值 | 说明 |
| --- | --- | --- | --- |
| `chat` | `user_input` | 必填 | 本轮提问 |
| `chat` | `keep_recent` | `KEEP_RECENT`（6） | 原文保留的对话条数，1 轮 = 2 条 |
| `summarize_old_messages` | `history` | 必填 | 完整历史（含 system） |
| `summarize_old_messages` | `keep_recent` | `KEEP_RECENT`（6） | 同上；建议取偶数，与「轮」边界对齐 |
| `summarize` | `text` | 必填 | 要压缩的文本，返回摘要字符串 |

模块级常量：`KEEP_RECENT`（保留条数）、`SUMMARY_PREFIX`（摘要标记，默认 `【此前对话摘要】`）、`last_messages`（调试用，记录最后一次发送的消息）。

`summarize()` 单独抽成函数有两个好处：职责单一；写测试时可以替换成假实现，验证逻辑而不花真实 API 费用。

## 运行报错对照

| 报错 | 原因 | 处理 |
| --- | --- | --- |
| `NameError: name 'client' is not defined` | 直接用了 `client.chat...` 但从未创建客户端 | 改为 `from run import get_client` + `get_client()` |
| `400 Empty input messages` | `messages` 是空列表 | 至少放一条消息；压缩后先检查是否为空 |
| 400 提示首条消息角色异常 | 窗口切在 assistant 上 | 保证窗口从 user 开始（见关键决策 ④） |
| 摘要里出现「此前对话摘要」字样 | 重压时没排除旧的摘要消息 | 按 `SUMMARY_PREFIX` 过滤后再拼接 |
| `KeyError: 'role'` | 历史里混入了结构不对的消息 | 检查构造历史的地方，或改用 `m.get("role")` |

## 可优化点

- **增量压缩**：现在是超阈值后每轮都重压一次。可改为「未压缩的原文先以原文带上，攒够一批才触发一次压缩」，省掉大部分摘要调用。
- **按 token 而非条数判断**：`keep_recent` 数的是条数，若每轮回答都很长，总 token 仍可能超限。可用 tokenizer 估算后再决定。
- **摘要质量可观测**：记录压缩前后的字数 / token 数，以及摘要内容，便于发现失真。
- **多会话隔离**：把模块级 `history` 改为 `Session` 类或 `{session_id: history}`，支持并发。
- **关键实体清单**：摘要 prompt 里要求单独输出「人名 / 数字 / 结论」三行，减少滚动压缩的信息损耗。
