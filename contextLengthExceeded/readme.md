# contextLengthExceeded — 策略一：滑动窗口

多轮对话上下文管理示例。**只把「人设 + 最近 `MAX_TURNS` 轮对话」发给模型**，更早的消息在发送时被裁掉——长度立刻有界，实现也最简单。

与策略二（`../contextLengthExceeded2/`，摘要压缩）互补：本示例「**只丢不记**」，策略二「有损但有记忆」。

## 要解决的问题

不管理历史会同时撞上三件事（与策略二完全相同，这是两种策略共同面对的起点）：

| 压力 | 表现 |
| --- | --- |
| 窗口上限 | 模型有上下文窗口上限（如 128K token），超出直接报错 |
| 成本 | 上下文每一轮都要重发，token 按量计费，历史越长越贵 |
| 注意力稀释 | 上下文越长，早期关键信息的权重越低（lost in the middle） |

## 核心思路

> **近期的原文保留，远期的历史直接不发送。**
>
> 发送给模型的上下文由两段构成：固定人设 + 最近 `MAX_TURNS` 轮的原文。超过窗口的轮次被丢弃，本地 `history` 仍保留完整记录。

```text
发给模型的 context（长度有界）            本地 history（全量保留，不发送）
┌────────────────────────────────┐       ┌──────────────────────┐
│ system    人设（永远保留）       │       │ u1 a1 u2 a2 u3 a3 …  │
│ user      最近第 N-2 轮提问      │  ◀──  │ 含已被裁掉的早期轮次    │
│ assistant …                    │       │ 只涨不裁，方便回溯      │
│ user      最近第 N 轮提问        │       └──────────────────────┘
└────────────────────────────────┘
     窗口 = 1 条人设 + 最近 max_turns × 2 条对话
```

一句话概括两种策略的分野：

| | 超过窗口的部分 | 结果 |
| --- | --- | --- |
| **策略一（本示例）** | 直接丢弃 | 长度稳定，早期信息**永久消失** |
| 策略二（摘要压缩） | 压成一条摘要 | 长度稳定，早期信息**有损保留** |

## 一轮对话里发生了什么

```text
1. chat(user_input)
   └─ history.append({"role": "user", ...})

2. trim_history(history, max_turns=MAX_TURNS)
   ├─ 挑出全部 system 消息 → system_msgs（不占窗口名额）
   ├─ 剩下的是对话 → dialog
   ├─ 三元表达式取末尾 2×max_turns 条：
   │    window = dialog[-max_turns * 2:] if max_turns > 0 else []
   ├─ 兜底：窗口首条不是 user 就丢掉它
   └─ 返回 system_msgs + window（列表相加，浅拷贝出新列表）

3. runDemo(messages=上一步的结果)
   └─ 只发送裁剪后的窗口

4. history.append({"role": "assistant", ...})
   └─ 本地 history 仍记全量，不裁剪
```

## 长度实测

同一份对话，**在同一个发送时点**对比「不管理」与「策略一」（默认 `MAX_TURNS = 20`，即窗口 40 条）：

| 轮次 | 不管理（条/字） | 策略一（条/字） | 被裁掉的轮次 |
| --- | --- | --- | --- |
| 1 | 2 / 36 | 2 / 36 | 无 |
| 5 | 10 / 216 | 10 / 216 | 无 |
| 10 | 20 / 443 | 20 / 443 | 无 |
| 20 | 40 / 923 | 40 / 923 | 无 |
| **21** | 42 / 971 | **40 / 926** | 第 1 轮 |
| 25 | 50 / 1163 | **40 / 938** | 第 1~5 轮 |
| 30 | 60 / 1403 | **40 / 950** | 第 1~10 轮 |

三条关键结论：

- **第 20 轮之前两者完全一样。** 窗口还没满，裁剪不生效——这也意味着**本示例默认参数下（只提 2 个问题、共 5 条消息）根本触发不了裁剪**。
- **第 21 轮起分道扬镳**：不管理线性增长（30 轮 1403 字），策略一稳定在 40 条 / 约 950 字。
- **被裁掉的是最早的轮次**，而且是永久丢弃——不管理是"全记得"，策略一是"只记得最近的"。

**早期信息丢失的临界点**（用户在第 1 轮说「我叫张三」，窗口 40 条）：

```text
第 19 轮 -> 「我叫张三」还在发给模型的消息里吗: True
第 20 轮 -> 「我叫张三」还在发给模型的消息里吗: False
```

这就是"只丢不记"的直接后果，也是策略二存在的理由。

## 与策略二对比

| 维度 | 策略一：滑动窗口 | 策略二：摘要压缩 |
| --- | --- | --- |
| 长度控制 | 稳定 | 稳定 |
| 早期信息 | **直接丢弃** | 保留要点（有损） |
| 额外 API 调用 | **无** | 超过阈值后每轮 1 次 |
| 实现复杂度 | 低（一个函数 10 行） | 中（要写摘要 prompt、防摘要失真） |
| 发送字数（40 轮） | 约 950 字 | 约 1200 字 |
| 适用 | 短会话、演示、调试 | 长会话、客服、陪伴、连续编码 |

策略一比策略二**省字数、省调用、省代码**，代价是"忘了就是真忘了"。选型标准很简单：**这段对话里，早期信息还会不会被用到？**

## 实现中的五个关键决策

**① 人设单独挑出，不占窗口名额**

```python
system_msgs = [m for m in history if m["role"] == "system"]
dialog      = [m for m in history if m["role"] != "system"]
return system_msgs + window
```

人设排在第 0 位，如果直接对 `history` 整体切片，**最先被裁掉的恰恰是人设**——模型立刻"性格大变"。所以先把 system 挑出来单独保管，切完再拼回最前面。

**② 一轮 = 2 条，所以切片长度要乘 2**

```python
window = dialog[-max_turns * 2:] if max_turns > 0 else []
```

一轮完整对话 = 一条 `user` + 一条 `assistant`。`max_turns=6` 对应 12 条。

**③ `max_turns > 0` 的守卫：避开 `-0` 陷阱**

```python
max_turns = 0
dialog[-max_turns * 2:]     # -0 就是 0 → dialog[0:] → 返回全部历史！
```

`-0 == 0`，切片 `[0:]` 是**从头取到尾**，跟"什么都不带"完全相反。加上 `> 0` 的判断后这个边界被显式挡住。三元表达式**只对选中的那一侧求值**，所以条件为假时切片根本不会执行——这正是它能防住 `-0` 的根本原因。

**④ 窗口必须切在 user 边界上**

```python
if window and window[0]["role"] != "user":
    window = window[1:]
```

一轮对话是"问 + 答"两件事，从中间切开会留下孤立的 `assistant` 消息，部分模型遇到"首条是 assistant"直接返回 400。**宁可少带一条，不能带半轮。**

> **一个值得知道的细节**：发送那一刻，`dialog` 的长度总是**奇数**（最后一条提问还没有回复），而切片长度 `max_turns × 2` 永远是偶数。奇数长度列表取末尾偶数条，**必然落在 assistant 上**，于是兜底会再吃掉一条——实际窗口是 `max_turns − 1` 轮 + 当前提问。不算 bug（结构依然合法），但调参数时要知道它比你写的少一轮。

**⑤ 发送与存储分离**

`trim_history` 返回的是新列表（列表相加是浅拷贝），**不改动 `history` 本身**。本地保留全量原文，只是不发送。好处是随时能换策略、能回溯真实对话；代价是内存不回收。

## 要付的代价

| 代价 | 说明 | 缓解 |
| --- | --- | --- |
| 早期信息永久丢失 | 裁掉就没了，模型完全想不起来（第 20 轮忘掉第 1 轮说的话） | 换策略二，或把关键事实固化进人设 |
| 按「条数」而非 token | 每轮回答都很长时，40 条也可能撞上限 | 用 tokenizer 估算，或把 `MAX_TURNS` 调小 |
| 本地内存只涨不降 | `history` 是模块级全局，30 轮已 61 条 | 超长会话落盘或定期裁剪 |
| 单会话限制 | 全局 `history`，多个用户会串话 | 做服务时挪进 session 对象或字典 |

## MAX_TURNS 怎么选

30 轮之后窗口的稳态长度（`1 + 2 × max_turns`）：

| `max_turns` | 发送条数 | 保留对话 | 适用 |
| --- | --- | --- | --- |
| 0 | 1 | 0 条（只剩人设） | 只要人设、不要历史 |
| 3 | 7 | 6 条 | 短问答、演示、调试 |
| 6 | 13 | 12 条 | 与策略二的 `keep_recent=6` 对齐，便于对比 |
| **20（默认）** | 41 | 40 条 | 长会话，但要算清楚 token |
| 50 | 101 | 100 条 | 基本等于不管理 |

调参时记住两件事：**发送条数 = 1 + 2 × max_turns**；以及上面④提到的"实际比设定少一轮"。

## 如何运行

**在本目录内执行**（`run.py` 与本文件同目录）：

```bash
python index.py
```

示例连续提两个问题，真实输出：

```text
问：什么是 JSON？
答：JSON（JavaScript Object Notation）是一种轻量级、基于文本的数据交换格式，用键值对和数组表示结构化数据…

问：什么是 HTTP 状态码？
答：HTTP 状态码是服务器在响应客户端请求时返回的三位数字代码，用于表示请求的处理结果…
```

> **默认参数下看不到裁剪效果。** `MAX_TURNS = 20` 意味着 40 条窗口，而两轮问答只产生 5 条消息，`trim_history` 会原样返回全部内容。想看它工作，把 `MAX_TURNS` 改成 `2` 再跑，或自己多问几轮。

> 本目录名含连字符（`contextLengthExceeded`），不是合法的 Python 包名，无法从项目根写 `from contextLengthExceeded.run import runDemo`。同目录内 `from run import runDemo` 不受影响。

**在别的文件里调用**

```python
from index import chat, trim_history

answer = chat("什么是 JSON？")                  # 追加一轮，返回回答正文
ctx = trim_history(history, max_turns=3)       # 只看裁剪后的窗口，不发请求
```

**参数**

| 函数 | 参数 | 默认值 | 说明 |
| --- | --- | --- | --- |
| `chat` | `user_input` | 必填 | 本轮提问 |
| `trim_history` | `history` | 必填 | 完整历史（含 system） |
| `trim_history` | `max_turns` | `MAX_TURNS`（20） | 保留的对话轮数，1 轮 = 2 条 |

模块级常量：`MAX_TURNS`（保留轮数）。注意它作为默认值在 `def` 时就被求值了，**改模块常量不会同步更新已有的默认值**，跨文件调用时建议显式传参。

## 接口说明

| 参数 | 值 |
| --- | --- |
| `base_url` | `https://api.deepseek.com` |
| `model` | 读环境变量 `MODEL`，未设置时退回 `deepseek-flash` |
| 接口路径 | `/chat/completions` |

裁剪只在本地完成，**不产生任何额外 API 调用**——这是策略一相对策略二最实在的优势。

## 运行报错对照

| 报错 | 原因 | 处理 |
| --- | --- | --- |
| 400 提示首条消息角色异常 | 窗口切在 assistant 上 | 已内置兜底（见关键决策④），检查是否手动改过切片逻辑 |
| `400 Empty input messages` | `messages` 是空列表 | 正常路径至少返回 1 条人设；但 `history` 本身为空时 `trim_history([])` 返回 `[]`，调用前先判空 |
| 模型答非所问 / 忘记前面说过的话 | 早期轮次已被裁掉（设计如此） | 关键事实写进人设，或换策略二 |
| `KeyError: 'role'` | 历史里混入了结构不对的消息 | 检查构造历史的地方，或改用 `m.get("role")` |

## 可优化点

- **按 token 而非条数判断**：`max_turns` 数的是条数，若每轮回答都很长，总 token 仍可能超限。可用 tokenizer 估算后再决定窗口大小。
- **关键事实固化**：把用户第一轮说的名字、编号、偏好提取出来写进 `system`，它永远占一个固定名额，不会被裁——这是用极低成本补住"忘了就是真忘了"的短板。
- **兜底改为"挪起点"而非丢弃**：现在是 `window = window[1:]`，若交替被打破（连续两条 assistant），丢一条不够。改用 `while` 往后挪到 user 更稳。
- **被裁内容落盘**：裁掉的早期轮次存到文件或数据库，需要时再召回——这其实就是策略二的思路，也是往 RAG 演进的第一步。
- **多会话隔离**：把模块级 `history` 改为 `Session` 类或 `{session_id: history}`，支持并发。
